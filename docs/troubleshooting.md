## B. 온디바이스 채보 전환

### B-1. 녹음 포맷이 피치 추정에 쓸 수 없는 형식이었다

✅ 반영(1단계) · 📝 실제 기기의 입력 처리(자동 이득·잡음 억제)는 기기 체크리스트 1-6

- **문제**: 기존 녹음은 `MediaRecorder` + 3GP / **AMR-NB** 였다. AMR-NB는 8kHz 음성 통화용 손실 코덱이다.
- **원인**: 서버 업로드 시절에는 용량이 중요했고, 서버 쪽에서 디코딩했다. 온디바이스 모델(Basic Pitch)은 22,050Hz mono PCM 파형을 입력으로 받는다. 8kHz로는 나이퀴스트가 4kHz라 배음 정보가 잘리고, 코덱 왜곡도 피치 추정에 불리하다.
- **검토한 선택지**
  1. 3GP를 그대로 두고 `MediaCodec`으로 디코딩 → 이미 잃은 정보는 되돌릴 수 없다.
  2. `AudioRecord`로 PCM을 직접 받아 WAV로 저장 → 채택.
- **결정**
  - 22,050Hz를 먼저 시도하고, 기기가 거부하면 44,100Hz(Android가 모든 기기에서 보장하는 유일한 레이트)로 녹음한 뒤 채보할 때 2배 다운샘플한다.
  - 다운샘플러는 Blackman 창 sinc 저역통과(63탭) + 2:1 솎아내기. 음성 대역(100Hz~4kHz) 이득 ±0.5dB, 13kHz 이상 -40dB 이하를 테스트로 고정했다.
  - 저장 위치를 `externalCacheDir`에서 `filesDir/recordings`로 옮긴다. 캐시는 저장 공간이 부족하면 OS가 지울 수 있어, 사용자의 녹음이 사라지고 DB에는 빈 경로만 남는다.
- **남은 과제** 📝: 실제 기기에서 22,050Hz가 실패하는 기종 확인, 입력 소스(`VOICE_RECOGNITION` vs `MIC`)별 자동 이득·잡음 억제 영향.

### B-2. TFLite 2.17이 Play의 16KB 페이지 요구를 만족하지 못했다

✅ 반영·검증 완료

- **문제**: 프로젝트에 이미 `org.tensorflow:tensorflow-lite:2.17.0`이 들어 있었고, `litert-support-api`를 `exclude` 해야 빌드되는 상태였다.
- **원인 추적**
  - Gradle 캐시의 POM을 열어 보니 `tensorflow-lite:2.17.0`은 실체가 없는 **relocation** 이었다: `com.google.ai.edge.litert:litert:1.0.1`로 옮겨져 있다. TFLite가 LiteRT로 이름을 바꾸는 과도기라 두 그룹의 아티팩트가 충돌했고, 그래서 `exclude`가 필요했던 것.
  - targetSdk 35 앱은 Google Play에서 16KB 메모리 페이지를 지원해야 한다. AAR 안의 `.so` ELF 헤더에서 `PT_LOAD` 세그먼트의 정렬(`p_align`)을 직접 읽어 확인했다.

    | 버전 | arm64-v8a | armeabi-v7a | x86 | x86_64 |
    |---|---|---|---|---|
    | litert 1.0.1 (= tflite 2.17) | 16KB | **4KB** | **4KB** | **4KB** |
    | litert 1.4.2 | 16KB | 16KB | 16KB | 16KB |

- **검토한 선택지**
  1. LiteRT 2.x 최신(2.4.0) → API가 `CompiledModel` 중심으로 바뀌어 기존 `Interpreter` 사용법과 다르다. 작은 모델 하나 돌리는 데 이점이 적다.
  2. LiteRT **1.4.2**(1.x 마지막) → `Interpreter` API 그대로, 모든 ABI 16KB 정렬. 채택.
- **결정**: `tensorflow-lite`, `tensorflow-lite-gpu`, `tensorflow-lite-support`를 지우고 `litert:1.4.2` 하나만 쓴다. GPU delegate는 쓰지 않는다(모델이 작고, 그래프 안 CQT 연산의 GPU 지원이 불확실). support 라이브러리도 `ByteBuffer`만 쓰면 되어 필요 없다.
- **검증**: 에뮬레이터(x86_64)에서 LiteRT 추론 결과가 Python 결과와 1e-3 이내로 일치(`BasicPitchModelGoldenTest`).

### B-3. 모델 출력 텐서 순서가 이름 순서와 달랐다

✅ 반영·검증 완료

- **문제**: Basic Pitch 출력은 `note`, `onset`, `contour` 세 개다. 흔히 출력 인덱스 0·1·2로 받는데, 실제 `nmp.tflite`를 Python 인터프리터로 열어 보니 출력 텐서 인덱스 순서가 `onset(285) / note(289) / contour(274)` 식으로 이름 순서와 맞지 않았다. 원본 코드의 ONNX 경로도 `StatefulPartitionedCall:1/2/0`처럼 순서를 따로 매핑하고 있었다.
- **결정**: 인덱스가 아니라 **시그니처 이름**으로 접근한다(`runSignature`, 시그니처 `serving_default`, 입력 `input_2`, 출력 `note`/`onset`/`contour`). 모델 파일을 바꿔도 순서에 의존하지 않는다.
- **같이 확인한 것**: 모든 연산이 builtin(CONV_2D, LOG, MIRROR_PAD 등)이라 Flex delegate가 필요 없다. CQT가 그래프 안에 들어 있어 Kotlin에서 스펙트로그램을 만들 필요가 없다.

### B-4. Python 후처리를 Kotlin으로 옮기며 결과를 똑같이 맞추기

✅ 반영·검증 완료

- **문제**: Basic Pitch는 모델 출력(확률 맵)을 음표로 바꾸는 후처리(`note_creation.py`)가 Python/numpy로만 있다. 옮기면서 미묘하게 다르면, 나중에 "모델이 문제인지 포팅이 문제인지" 구분할 수 없다.
- **원본과 결과가 갈릴 수 있었던 지점**
  - numpy 기본 타입: 모델 출력은 float32지만 `remaining_energy`, 추정 onset은 `np.zeros`(float64)에서 시작해 **float64로 계산**된다. 임계값 비교도 float64. → Kotlin도 `DoubleArray`로 계산.
  - 처리 순서: `np.where` 결과를 뒤집어서 onset을 **시간 내림차순, 같은 시간이면 음높이 내림차순**으로 처리한다. 순서가 바뀌면 남은 에너지를 지우는 순서가 달라져 결과가 달라진다.
  - `scipy.signal.argrelmax`: 시간축의 **엄격한** 극대, 양 끝 프레임은 극대가 아니다(`mode='clip'`).
  - melodia 단계의 `np.argmax`: 같은 값이면 평탄화 배열의 **첫 번째**.
  - `np.round`는 짝수 반올림(banker's rounding). Kotlin `kotlin.math.round`도 짝수 반올림이라 그대로 쓸 수 있다(`Math.round`는 아니다).
- **성능 변경(결과는 동일)**: 원본 melodia는 반복마다 전체 배열 argmax를 구한다(O(셀 수 × 반복)). 값은 0으로만 바뀌므로, 임계값을 넘는 칸을 (값 내림차순, 인덱스 오름차순)으로 한 번 정렬해 두고 살아 있는 첫 칸을 고르면 같은 순서가 된다.
- **의도적으로 다르게 한 곳**: 원본은 프레임 차분의 최댓값이 0이면(완전 무음) 0/0 = NaN이 퍼진다. 포팅은 이 경우 차분을 0으로 둔다(테스트로 고정).
- **알고 있지만 원본을 따른 곳**: `model_frames_to_time`은 창 경계 보정 주기를 172프레임으로 잡지만 unwrap 뒤 창당 프레임은 142다. 30초 녹음에서 수십 ms 어긋날 수 있다. 위상 추정(B-7)이 흡수하는 범위라 원본과 같게 두었다.
- **검증**: 골든 테스트. Python으로 만든 5개 케이스 × 3개 파라미터 조합에서 음표의 시작·끝 프레임, 음높이, 진폭(1e-5), 초 단위 시각(1e-9)이 **순서까지** 일치.

### B-5. 테스트가 정말 차이를 잡는지: 변이 검사에서 속은 경험

✅

- **문제**: B-4의 골든 테스트가 처음부터 한 번에 통과했다. 테스트가 너무 느슨한 건 아닌지 확인하려고 코드를 일부러 망가뜨려 봤다(변이 검사).
- **첫 시도에서 속은 것**
  1. `energyTolerance`를 11 → 10으로 바꿨는데 테스트가 통과했다.
  2. 원인 하나: 빌드가 1초 안에 끝났다. `org.gradle.caching=true` 때문에 **같은 입력의 테스트 결과를 캐시에서 꺼내 왔다**(첫 변이 실행에서 만들어진 캐시). 테스트는 실제로 돌지 않았다.
  3. 원인 둘: 이 변이는 애초에 약했다. 허용치 11과 10은 "정확히 10프레임짜리 끊김"이 있을 때만 결과가 갈린다. 합성 데이터에는 그런 구간이 없다.
- **결정**: 결과에 확실히 영향을 주는 변이(이웃 음높이의 에너지를 지우는 줄 제거)로 바꾸고 `--rerun`으로 캐시를 건너뛰었다 → 2개 실패. 원복 → 통과.
- **배운 점**: "테스트가 통과했다"를 볼 때 실제로 돌았는지(실행 시간·`--rerun`)와, 변이가 그 테스트 데이터에서 실제로 결과를 바꾸는지를 같이 봐야 한다.

### B-6. 다성 모델로 허밍을 채보하면 같은 음이 잘게 쪼개진다

✅ 반영 · 📝 실제 허밍으로 재튜닝 필요

- **문제**: 정답 19음인 합성 멜로디에서 Basic Pitch가 27개 음을 냈다.
- **원인 분석**: 처음엔 배음(옥타브 위)이 잡힌 줄 알았지만, 출력을 정답과 나란히 놓고 보니 **음높이는 전부 맞았고**, 늘어난 것은 **같은 음이 끝과 시작이 딱 붙은 채 쪼개진 조각**이었다. 쪼개진 간격이 약 0.18초 = 비브라토 주기(5.5Hz). 비브라토 때문에 onset 확률이 0.5~0.7로 튀어 새 음으로 인식된 것.
- **어려운 점**: 정답의 **진짜 반복음**(같은 음을 두 번 부름)도 Basic Pitch 출력에서는 똑같이 "끝과 시작이 붙은 같은 음"으로 나온다. 붙어 있으면 무조건 합치면 진짜 반복음이 사라진다.
- **데이터로 기준 찾기**: 경계 ±4프레임에서 note 확률 최솟값과 onset 확률 최댓값을 모든 같은 음 경계에 대해 뽑았다.

  | 경계 종류 | note 확률 최솟값 | 앞 음 진폭 대비 | onset 최댓값 |
  |---|---|---|---|
  | 진짜 반복음 | 0.36 | **46%** | 0.92 |
  | 비브라토 조각 | 0.87~0.91 | **97% 이상** | 0.51~0.70 |

  진짜 반복음은 소리를 끊었다 다시 내니 경계에서 **에너지가 꺼진다**. 비브라토 조각은 소리가 이어져 있어 꺼지지 않는다.
- **결정**: 단성화(`MonophonicReducer`)에서 같은 음 두 조각 사이 간격이 3프레임 이하이고, 경계의 note 확률 최솟값이 두 조각 진폭 중 작은 값의 **70% 이상**이면 합친다. 겹치는 서로 다른 음은 (진폭 × 길이)가 큰 쪽을 남긴다.
- **남은 과제** 📝: 기준값 0.7은 깨끗한 합성 데이터에서 정했다. 실제 허밍(자음 없이 "음~"으로 이어 부르는 반복음 등)에서 다시 맞춰야 할 1순위 값이다.

### B-7. 기기마다 다른 녹음·재생 지연과 박 격자 맞추기

✅ 반영 · 📝 블루투스 지연 확인 필요

- **문제**: 사용자가 BPM을 고르고 메트로놈 카운트인 뒤에 부르면, 녹음 파일의 0초가 첫 박이어야 한다. 그런데 `AudioRecord` 시작 지연, 클릭 재생 지연, 사람이 소리를 듣고 반응하는 시간이 기기·사람마다 다르다. 120 BPM에서 16분음표가 125ms라 수십 ms 오차도 격자를 한 칸 밀 수 있다.
- **검토한 선택지**
  1. 기기 지연을 측정·보정(루프백 측정 등) → 기기마다 다르고 블루투스는 더 크다. 사람의 반응 지연은 측정으로 못 없앤다.
  2. 템포까지 자동 추정 → 허밍에서 불안정하다(박이 뚜렷하지 않다). 그래서 템포는 사용자가 정한다.
  3. **템포는 알고 있으니 남은 미지수는 위상(오프셋) 하나** → onset들이 격자에 가장 잘 맞는 위상을 탐색. 채택.
- **결정**: 위상 φ를 -0.3~0.7박 범위에서 2ms 간격으로 훑어, `Σ 진폭 × (16분 격자 오차² + 0.25·8분 격자 오차² + 0.1·박 격자 오차²)`가 최소인 φ를 고른다.
  - 16분 격자만 보면 φ와 φ+16분이 똑같이 잘 맞아 **박 위치가 모호**하다. 8분·박 격자에 가중치를 더해 "음은 대개 박이나 8분 위치에서 시작한다"는 사전 지식을 넣었다.
  - 탐색 범위를 뒤쪽으로 넓게 잡은 이유: 지연은 대개 소리를 늦게 만든다.
- **검증**: BPM 60·90·120·140 × 지연 -0.2·0·0.15·0.4·0.6박 × 흔들림 3종 = 60개 조합에서 모두 정답 복원, 위상 오차 1/8박 이내. 합성 허밍 3건에서 위상 오차 0~33ms(33ms는 글리산도 때문에 onset이 늦게 잡힌 레가토 케이스).
- **남은 과제** 📝: 블루투스 이어폰은 지연이 200ms 이상일 수 있다. 빠른 템포에서 0.7박을 넘으면 악보 전체가 한 박 밀린다.

### B-8. 허밍은 적힌 길이보다 짧게 소리 낸다

✅

- **문제**: 2분음표(8 step)가 7 step으로 나왔다. 마지막 음이었다.
- **원인**: 사람은 다음 음이나 숨쉬기 전에 음을 조금 일찍 끊는다(합성 데이터는 적힌 길이의 85%만 소리 냄). 중간 음은 "다음 음까지의 짧은 빈틈을 메운다" 규칙으로 보정되고 있었지만, **마지막 음과 쉼표 앞 음은 다음 음이 없어서** 규칙이 적용되지 않았다.
- **결정**: 쉼표 앞·마지막 음은 끝이 다음 박 경계 바로 앞(빈틈 허용치 이내)이면 박 경계까지 늘린다. 실제 쉼표(예: 1박)는 허용치보다 길어서 보존된다.
- **한계**: 65%만 소리 낸 4분음표는 8분음표로 나온다. 소리만으로는 의도한 길이를 알 수 없는 경우라 받아들였다(흐트러진 케이스 21음 중 2음).

### B-9. 합성 데이터에 과적합하지 않았는지

✅

- **문제**: B-6~B-8의 규칙은 합성 데이터 결과를 보고 다듬었다. 그 데이터에서만 잘 맞는 규칙일 수 있다.
- **결정**: 규칙을 만든 데이터와 다른 **흐트러진 케이스**를 따로 만들어 평가했다. 박자 흔들림 ±40ms, 소리 길이 65~95%, 음정 오차 ±25cent, 큰 지연 0.32초, 더 큰 잡음. 정확히 같기를 요구하지 않고 음 단위 정확도로 하한선을 둔다(시작 위치 90%, 길이 75%, 없는 음 2개 이하).
- **결과**: 시작 위치 21/21, 길이 19/21, 없는 음 0, 위상 0.318초(정답 0.32), 조성 D major 정답.
- **한계**: 여전히 합성이다. 실제 허밍 녹음이 생기면 같은 방식으로 골든 케이스에 추가한다.

### B-10. 실제 허밍 녹음 없이 정답 데이터 만들기

✅

- **문제**: 개발 시점에 실제 허밍 녹음이 없었다. 기기·사람 없이 검증할 방법이 필요했다.
- **결정**: Python으로 정답 악보를 알고 있는 "허밍풍" 오디오를 합성한다(`tools/basic_pitch_golden/make_golden.py`). 배음 6개, 시작 150ms 뒤부터 서서히 커지는 비브라토(5.5Hz ±25cent), 어택·릴리스 엔벨로프, 숨소리 잡음, 시작 지연, 레가토 케이스는 60ms 글리산도.
- **만들다 생긴 버그**: 처음에는 녹음 길이를 손으로 적었는데 악보보다 짧아서 마지막 음들이 잘렸다. 정답 악보에는 있는데 오디오에는 없는 음이 생겨, 채보가 틀린 것처럼 보였다. → 길이를 `시작 지연 + 악보 길이 + 여유`로 계산하게 바꿨다. 기존 케이스의 난수 순서가 바뀌지 않았는지 파일 바이트 비교로 확인했다.

### B-11. 알고리즘 모듈의 object 설계와 관심사 분리

✅

- **배경**: 채보 알고리즘은 품질을 결정하는 곳이라 기기 없이 빠르게 테스트하고 싶었다. 그래서 `:core:music`을 **안드로이드·프로젝트 의존 없는 순수 JVM 모듈**로 만들고, 모델 실행(`:core:ml`, 네이티브라 안드로이드 모듈)과 분리했다. domain은 둘 다 모르고 `TranscriptionRepository` 인터페이스만 안다.
- **첫 설계**: 단계(`NoteCreation`, `MonophonicReducer`, `Quantizer`, `KeyEstimator`)와 진입점(`HummingTranscriber`)을 모두 `object`로 만들었다. 상태가 없는 순수 함수라 인스턴스가 담을 것이 없다는 이유.
  - 생명주기: `object`는 처음 접근할 때 만들어져 프로세스 끝까지 살지만, Context·버퍼·리스너를 잡지 않아 누수될 것이 없다. 호출마다 지역 변수만 써서 스레드 안전하다. 생명주기가 있는 유일한 자원(LiteRT 인터프리터)은 처음부터 `Closeable` class로 만들고 DI 싱글턴으로 둔다.
- **리뷰에서 나온 문제**
  1. **경계의 정적 결합**: data 계층이 `HummingTranscriber.transcribe(...)`를 이름으로 직접 부른다. 생성자에 드러나지 않는 숨은 의존이라, 저장소를 테스트할 때 채보를 가짜로 바꿀 수 없고 Hilt 주입 방식과도 어긋난다(DIP 위반).
  2. **설정값 산재**: 튜닝값(`TranscriptionParams`)을 호출마다 기본값으로 넘긴다. 나중에 사용자 설정이 생기면 넣을 자리가 없다.
  3. **패키지 혼재**: `score` 패키지에 모델(`Score`, `Key`)과 직렬화(`MusicXmlWriter`, `MidiWriter`)가 섞여 있다.
- **정한 원칙**: *바뀔 수 있거나 비용이 큰 것은 주입하고, 결정적이고 값싼 순수 유틸리티는 직접 호출한다.*

  | 대상 | 성격 | 처리 |
  |---|---|---|
  | LiteRT 모델 | 네이티브, 느림, 생명주기, 교체 가능 | 인터페이스로 주입 |
  | 채보 진입점 | 전략·튜닝값, 교체 가능 | `ScoreTranscriber` 인터페이스로 주입 |
  | 안쪽 단계 | 상태 없는 순수 함수 | `object` 유지 |
  | WAV·리샘플러·MusicXML·MIDI | 정해진 형식 변환 | 직접 호출 |

- **결정**
  - `ScoreTranscriber` 인터페이스 + `class HummingTranscriber(params)`. 튜닝값은 생성할 때 한 번 받는다.
  - 직렬화는 `music.export` 패키지로 분리(`score`는 모델만).
  - 모델도 인터페이스와 LiteRT 구현으로 나눈다(예정).
- **검증**: 진입점은 인터페이스 타입으로 테스트하고, 생성자로 준 설정이 실제로 쓰이는지 테스트로 고정.

### B-12. 메트로놈 소리·진동이 마이크로 들어간다

✅ 반영(1단계) · 📝 이어폰·블루투스에서의 클릭 누설은 기기 체크리스트 1-3

- **문제**: 녹음 중 스피커로 클릭을 틀면 마이크로 들어가 Basic Pitch가 클릭을 음표로 잡을 수 있다(클릭 1~1.6kHz는 사람 목소리 배음 대역).
- **검토한 선택지**
  1. 녹음 중 클릭을 계속 틀고 후처리에서 제거 → 클릭 제거 로직이 새로 필요하고, 목소리와 겹치면 어렵다.
  2. 카운트인만 소리, 녹음 중은 화면·진동으로 박 표시
  3. 이어폰이 연결됐을 때만 녹음 중 클릭, 아니면 2번 → 채택.
- **추가로 바꾼 것**: 녹음 중 **진동도 끈다**. 진동 모터 소리(대략 150~250Hz)가 기기 몸체를 통해 마이크로 들어가는데, 이 대역은 사람 목소리 기본 주파수 대역이라 음으로 잡힐 수 있다. 진동은 카운트인에만 쓰고, 녹음 중 박은 화면 표시로만 보여 준다.
- **구현 메모**: 메트로놈은 `SoundPool` 대신 `AudioTrack` 스트림에 클릭 PCM을 샘플 단위로 이어 써서 박 간격이 흔들리지 않게 한다. 박 표시는 마이크 샘플 수(녹음 시계)로 센다.
- **남은 과제** 📝: 실제 기기에서 이어폰 클릭의 마이크 누설, 진동 없이 화면만으로 박을 따라 부를 수 있는지 사용성 확인.

### B-13. DataStore 단위 테스트가 Windows에서만 실패했다

✅

- **문제**: 마지막 녹음 BPM 저장(`UserPreferencesRepositoryImpl`)을 JVM 테스트로 검증하는데, 한 테스트 안에서 두 번째로 저장할 때 `IOException: Unable to rename ...preferences_pb.tmp to ...preferences_pb`가 났다. 메시지는 "DataStore 인스턴스가 여러 개일 수 있다"고 안내했지만 인스턴스는 하나였다.
- **원인**: DataStore는 임시 파일(`.tmp`)에 쓴 뒤 원래 이름으로 바꿔 원자적으로 저장한다. Windows에서는 대상 파일이 이미 있으면 이름 바꾸기가 실패한다. 첫 저장은 대상 파일이 없어 성공하고, 두 번째부터 실패한다. 앱이 도는 Android(Linux)와 CI(Ubuntu)에서는 덮어쓰기가 되므로 앱 버그가 아니라 개발 PC 환경 문제다.
- **결정**: 테스트마다 저장을 한 번만 하도록 나눴다(최대값 클램프·최소값 클램프를 별도 테스트로). 이유를 테스트 주석에 남겼다.
- **배운 점**: 오류 메시지가 가리키는 원인(인스턴스 중복)과 실제 원인(OS의 rename 의미 차이)이 다를 수 있다. 같은 테스트가 첫 저장은 성공하고 두 번째만 실패한다는 패턴이 실마리였다.

### B-14. 테스트가 흔들려서 드러난 것: 스레드 전환을 누가 책임지나

✅

- **문제**: 녹음 화면 ViewModel 테스트 12개 중 "멈춘 뒤 저장 결과"를 보는 테스트가 실행할 때마다 일부만 실패했다(`Timed out after 5s of virtual time`). 통과한 것도 타이밍 운이었다.
- **원인**: `StopRecordingUseCase`(domain)가 안에서 `withContext(Dispatchers.IO)`로 스레드를 직접 바꾸고 있었다. 테스트는 가상 시간(`runTest`) 위에서 도는데 저장만 실제 IO 스레드에서 일어나, 가상 시간의 타임아웃이 실제 작업보다 먼저 끝났다. 기존 코드의 방식을 그대로 따른 것이었다.
- **진짜 문제**: 테스트를 고치기 전에 보니, "녹음기 정리(스레드 join·파일 헤더 쓰기)가 블로킹이라 IO 스레드가 필요하다"는 것은 **녹음기 구현(data)의 사정**인데 그 결정을 domain이 하고 있었다. 같은 이유로 `cancelRecording()`은 메인 스레드(`onCleared`, `ON_STOP`)에서 최대 1초 블로킹하고 있었다.
- **검토한 선택지**
  1. 테스트만 실제 시간으로 기다리게 → 통과는 하지만 설계 문제가 남는다.
  2. 디스패처를 유스케이스에 주입(`@IoDispatcher`) → 테스트는 결정적이 되지만, domain이 스레드를 고르는 구조는 그대로.
  3. **저장소를 main-safe하게**: `stopRecording()`을 `suspend`로 바꾸고 구현이 IO로 넘긴다. 유스케이스는 스레드를 모른다. → 채택. Android 공식 가이드의 "데이터 계층은 main-safe" 원칙과 맞다.
- **결정**
  - `RecordRepository.stopRecording()`은 `suspend`. 세션은 호출 즉시 떼어 내고(두 번 눌러도 한 번만 멈춤), 정리는 `withContext(Dispatchers.IO)`.
  - `cancelRecording()`은 `onCleared`처럼 코루틴을 못 쓰는 곳에서도 불리므로 `suspend`로 만들 수 없다 → 캡처만 즉시 멈추고 정리는 저장소의 백그라운드 스코프에서. 정리가 끝나기 전 새 녹음은 막는다(마이크를 두 번 잡지 않게).
  - 인터페이스 KDoc에 "구현은 main-safe해야 한다"를 계약으로 적었다.
- **결과**: 가짜 저장소는 즉시 돌려주므로 ViewModel 테스트가 테스트 디스패처 위에서 결정적으로 돈다.
- **배운 점**: 흔들리는(flaky) 테스트를 타임아웃 늘리기로 덮지 말고, 왜 비결정적인지 따라가면 설계 문제가 나온다.


### B-15. 기기 안 악보 렌더러(WebView) 초안의 세 가지 문제

✅ (실제 렌더링은 기기 테스트로 확인 예정)

- **배경**: 악보는 MusicXML로 저장하고, 앱 assets에 넣은 OpenSheetMusicDisplay(OSMD 3.0.0, BSD-3)로 WebView 안에서 SVG로 그린다. 네트워크는 쓰지 않는다. Compose Canvas로 직접 그리는 방법도 있지만 조표·임시표·붙임줄·마디 배치를 다시 구현해야 해서 비용이 크다.
- **초안을 검토하며 찾은 문제**
  1. **WebView 누수**: `AndroidView`에서 WebView를 만들기만 하고 `destroy()`를 부르지 않았다. WebView는 네이티브 렌더러를 잡고 있어 GC만으로는 바로 정리되지 않는다. 악보 화면을 열고 닫을 때마다 쌓인다. → `onRelease = { it.destroy() }`.
  2. **다시 그리지 않는 숨은 가정**: 페이지 로드가 끝날 때 한 번만 그리고 `update`는 비어 있었다. 지금은 화면마다 새로 만들어져서 드러나지 않지만, 같은 WebView에 다른 악보가 오면 예전 악보가 그대로 남는다. → 로드 전에 온 값은 보관했다가 로드 직후 그리고, 로드 뒤에는 값이 바뀔 때만 다시 그린다(`RenderState`).
  3. **핀치 줌과 높이 맞춤의 충돌**: WebView 높이를 악보 높이에 맞추고 바깥 화면이 스크롤하는 구조인데, 줌을 켜 두면 확대할 때 OSMD가 폭에 맞춰 다시 그리고 높이가 바뀌어 화면이 튄다. → 줌을 끈다. 확대가 필요해지면 OSMD의 `zoom` 옵션을 쓰는 쪽이 낫다.
- **같이 정한 것**
  - JS → 앱 통신은 높이·오류 두 가지만(`AndroidBridge`). 브리지 콜백은 WebView의 백그라운드 스레드에서 오므로 `post {}`로 메인 스레드로 넘긴다.
  - 악보 그림은 테마와 상관없이 흰 바탕(OSMD 기본 검은 악보). 다크 테마에서 악보만 반전시키면 인쇄·공유 결과와 달라진다.
  - 그리기 실패는 그 화면에서만 의미 있는 상태라 ViewModel이 아니라 화면이 들고 있는다(`remember(musicXml)`).
  - IDE 미리보기에서는 WebView를 만들 수 없어 `LocalInspectionMode`로 자리만 그린다.

### B-16. 악보를 꼭 WebView로 그려야 하나

✅ (2026-11-24 결정)

- **문제**: B-15까지 WebView + OSMD로 만들어 놓고, 렌더러 테스트를 짜기 전에 "이게 최선인가"를 다시 검토했다. WebView는 기동이 느리고, 기기마다 WebView 버전이 다르고, Compose 테마와 따로 놀고, 테스트가 어렵다.
- **판단의 전제**: 우리 악보는 단순하다. `core:music`의 결과는 단선율(`MonophonicReducer`), 성부 1개, 오선 1개이고, 박 격자에 양자화되어 있으며 마디 나누기·붙임줄은 `ScoreLayout`이 이미 한다. 화음·다성부·가사·셈여림은 없다. 그래서 범용 엔진과 직접 그리기 사이의 비용 차이가 보통보다 작다.
- **검토한 선택지**

  | | A. WebView + OSMD (현재) | B. Verovio 네이티브(NDK) → SVG → AndroidSVG | C. Compose Canvas 직접 렌더러 + SMuFL 폰트(Bravura) |
  |---|---|---|---|
  | 그리는 품질 | 좋음(범용 조판 엔진) | 매우 좋음 | 구현한 만큼(처음엔 투박) |
  | 구현 비용 | 이미 끝남 | 큼(C++ 빌드, ABI별 .so, JNI) | 중~큼(레이아웃 엔진 직접) |
  | APK 크기 | JS 약 1.5MB | 네이티브 라이브러리 + 폰트로 수 MB(ABI별) | 폰트 하나(수백 KB) |
  | 첫 표시 | WebView 기동·JS 파싱 지연 | 빠름 | 가장 빠름 |
  | 기기별 차이 | WebView 버전 영향 | 적음 | 거의 없음 |
  | 테마·접근성 | CSS로 따로 맞춰야 함 | 일부 | Compose 테마 그대로, 음표 탭·재생 하이라이트 자연스러움 |
  | 테스트 | 어려움(B-17) | 중간 | 가장 좋음(레이아웃은 JVM, 그림은 스크린샷) |
  | 라이선스 | BSD-3 | LGPL-3.0(동적 링크·고지 검토 필요) | Bravura는 SIL OFL |

  서버 렌더링은 INTERNET 권한을 뺀 방향(C-10)과 맞지 않아 제외했다. Verovio를 WebView에서 wasm으로 돌리는 것은 A의 단점을 그대로 가지면서 용량만 커진다.
- **결정**: **A를 유지한다.** C는 3단계(채보 연결) 이후의 선택 단계로 미룬다. B는 비용 대비 얻는 게 적어 제외.
  - 2단계는 이미 동작하는 상태로 커밋됐다. 지금 렌더러를 바꾸면 핵심 목표(실제 채보 연결)가 밀린다.
  - C의 가치(테스트 용이성, 테마 통합, 차별점)는 진짜지만, 실제 채보 결과가 흘러 들어와야 "무엇을 그려야 하는지"의 범위가 확정된다. C의 어려운 부분은 빔(8·16분음표 묶기), 음자리표 선택(허밍 음역이 낮으면 낮은음자리표), 조표·임시표 배치, 줄바꿈·마디 폭 배분이고, 빔 대신 꼬리로 시작하면 1차 범위가 줄어든다.
- **남은 과제** 📝: C(직접 렌더러)는 3단계 뒤에 실제 데이터로 범위를 정해 다시 판단한다.

### B-17. 엔진이 없는 WebView를 어떻게 테스트하나: 검증 대상과 나머지 나누기

✅

- **문제**: `ScoreWebView`를 테스트하려는데, 실제 렌더링을 보려면 에뮬레이터 계측 테스트가 필요하다. JVM에서 돌리는 Robolectric의 WebView는 **JS를 실행하지도 그리지도 않는 shadow**라 OSMD가 그리는지는 볼 수 없다.
- **설계 원칙(함께 정한 것)**: 테스트할 것(검증 대상)과 나머지를 먼저 나눈다. 검증 대상은 실제 객체로, 나머지는 테스트 대역으로. 실제 객체를 쓰기 어려우면 호출만 기록하는 spy로 흉내 낸다. 이전 오픈소스 기여(AnkiDroid)에서 이렇게 설계해 머지된 경험이 근거다. 여기에 세 가지를 덧붙였다.
  1. **우리가 가진 타입의 "나머지"는 mock보다 fake.** `FakeSheetMusicRepository`처럼 진짜처럼 동작하는 작은 구현을 끼우고, 테스트는 "무엇을 불렀나"가 아니라 "결과 상태"를 본다. mock의 `verify`는 내부 호출 순서에 묶여 리팩터링마다 깨진다. 호출 자체가 요구사항일 때(화면에서 빠지면 반드시 `destroy`)만 호출을 기록해 본다.
  2. **spy는 협력 객체에 쓰고 검증 대상 자체에는 쓰지 않는다.** 검증 대상을 spy로 감싸 일부를 stub하면 진짜도 가짜도 아닌 혼합물을 테스트하게 된다.
  3. **내 것이 아닌 타입(WebView)은 직접 mock하지 않는다.** Robolectric의 ShadowWebView가 엔진 없이 `loadUrl`·실행한 JS·`destroy`를 기록하므로 사실상 프레임워크가 제공하는 spy다. 그래서 mockk 없이 이 구조가 나온다.
- **나눈 결과**

  | 구분 | 대상 | 방법 |
  |---|---|---|
  | 검증 대상 | `ScoreRenderState`(언제 무엇을 JS로 보낼지), `renderScoreScript`(이스케이프) | 실제 객체(순수 로직) |
  | 검증 대상 | `ScoreWebView`의 연결: 설정, 처음 여는 URL, 브리지 → 화면 상태, 화면에서 빠질 때 `destroy` | 실제 컴포저블 |
  | 나머지 | WebView 엔진 | Robolectric shadow(호출 기록) |
  | 나머지 | `onRenderError` 콜백 | 직접 만든 기록용 람다 |
  | 범위 밖 | OSMD가 실제로 그리는지 | 기기 체크리스트(`docs/device-checklist.md`) |

- **테스트하기 쉽게 바꾼 것**: B-15의 `RenderState`는 `draw(view, xml)`에서 WebView를 직접 불렀다. 이를 "지금 실행할 스크립트를 돌려주는" `ScoreRenderState`로 바꿔 WebView를 모르게 했다(검증 대상을 실제 객체로 테스트할 수 있게 경계를 옮김). JS 브리지의 익명 객체는 `ScoreBridge`로 이름을 붙여 테스트가 `getJavascriptInterface`로 꺼내 바로 부르게 했다(리플렉션 불필요). 동작은 그대로다.
- **진행 중 부딪힌 것**
  1. **WebView 높이가 0으로 나왔다.** Robolectric은 Compose 안의 WebView(View)를 실제로 배치하지 않는다. → 높이는 테스트에서 감싼 Compose 박스의 크기(`assertHeightIsEqualTo`)로 본다. 우리가 검증하려는 것은 "JS가 알린 높이 → Compose 높이"라는 연결이라 이쪽이 오히려 대상에 맞다.
  2. **640dp를 알렸는데 470dp가 나왔다.** 연결은 동작했고, Robolectric 기본 화면(320×470dp)에 잘린 것. → 화면 안에 드는 값(320)으로 테스트.
  3. **변이 검사에서 놓친 테스트.** 실제 코드를 일부러 4군데 망가뜨려(`destroy` 제거, 파일 접근 차단 제거, 같은 XML 재그리기 방지 제거, 0 이하 높이 방지 제거) 테스트가 잡는지 봤다. "0 이하 높이는 무시" 테스트가 마지막 변이를 놓쳤다. 처음 상태에서 0을 받으면 어차피 최소 높이로 돌아가 구분이 안 됐던 것. → 실제로 지켜야 할 동작인 "높이를 받은 뒤 0이 와도 줄지 않는다"로 고쳐 4개 모두 잡는다(B-5와 같은 교훈).
- **결과**: `feature:sheetmusic` 21개(ViewModel 8, `ScoreRenderState` 5, `ScoreWebView` 8). 에뮬레이터 없이 JVM에서 돈다. Robolectric 4.18.1(SDK 37 지원).

### B-18. 화면을 떠나도 계속되는 채보: 백그라운드 작업 설계

✅ 구현·테스트 완료 (3-1 저장소, 3-2 WorkManager, 3-3 라이브러리 화면) · 📝 기기 확인은 `docs/device-checklist.md` 2절

- **문제**: 초안(`LibraryViewModel`)은 채보를 `viewModelScope`에서 돌렸다. 라이브러리 화면을 떠나면 ViewModel이 지워지며 채보가 취소되고, 진행 상태도 사라진다. 채보는 수 초~수십 초 걸리는 CPU 작업이라 사용자가 기다리는 동안 다른 화면에 갈 수 있어야 한다. 앞서 "알림 없이(A안), 라이브러리 항목에 대기 상태가 남는다"로 정했다.
- **구조: 작업 하나 안은 파이프라인, 녹음 하나의 수명은 상태 기계**
  - 파이프라인(분기 없이 한 줄): `WAV 읽기 → 리샘플 → 추론(Basic Pitch) → 채보(ScoreTranscriber) → 파일 쓰기 → DB 저장`. 단계마다 진행률 비중(추론이 약 80%)을 두고, 단계 사이마다 취소를 확인하며, 실패는 이유(`NO_NOTES`, `RECORD_GONE`, `OTHER`)로 바꿔 넘긴다.
  - 상태 기계: `Idle → Queued → Running(stage, progress) → (Room에 악보) / Failed(reason)`, `Failed → Queued`(다시 시도), 악보 삭제 → `Idle`. 전이는 Worker만 일으키고, UI는 (작업 상태, 악보 유무) 두 값으로 화면 상태를 계산만 한다.
  - **성공은 작업 상태로 기억하지 않는다.** "Room에 그 녹음의 악보가 있다"가 곧 성공이다. WorkManager가 오래된 작업 기록을 지워도 화면이 흔들리지 않는다.
  - 상태 기계를 따로 프레임워크로 만들지 않는다. 전이를 실제로 지키는 것은 WorkManager이고, 우리 몫은 `WorkInfo → TranscriptionJob`, `(job, score) → 항목 상태` 두 순수 함수다. 표를 그대로 테스트로 옮길 수 있다.

    | WorkInfo | TranscriptionJob |
    |---|---|
    | ENQUEUED, BLOCKED | Queued |
    | RUNNING + 진행 정보 `WAITING` | Queued(모델 대기) |
    | RUNNING | Running(stage, progress) |
    | FAILED | Failed(output Data의 reason) |
    | SUCCEEDED, CANCELLED | 없음(화면 상태는 Room이 결정) |

- **결정 1: 진행 중 상태를 어디에 둘까**
  - (a) WorkManager의 WorkInfo를 그대로 쓰고 결과(악보)만 Room. (b) Room에 작업 테이블을 따로 둔다.
  - (b)는 DB v9 마이그레이션이 필요하고, 프로세스가 죽으면 RUNNING으로 남은 행을 WorkManager의 실제 상태와 직접 맞춰야 한다(진실이 두 곳). → **(a)**. 단 domain·feature는 WorkManager를 모르게 `TranscriptionScheduler { enqueue(recordId); observeJobs(): Flow<Map<Int, TranscriptionJob>> }`로 감싼다.
- **결정 2: expedited 작업을 쓸까** (처음 계획을 바꿈)
  - 처음 계획은 expedited worker였다. 그런데 API 31 미만(minSdk 26)에서 expedited 작업은 foreground service로 돌아 **알림이 반드시 필요하다**(`getForegroundInfo`). "알림 없음" 결정과 충돌한다.
  - → **일반 OneTimeWork**. 제약 조건이 없으면 앱이 앞에 있을 때 거의 바로 시작하고, 실행 시간 제한(10분)도 채보에 비해 넉넉하다. 사용자가 직접 누른 작업이라 충전·배터리 같은 제약도 걸지 않는다.
- **결정 3: 대기열과 직렬화** (처음 추천을 바꿈)
  - 모델(LiteRT 인터프리터)은 싱글턴이고 동시에 호출하면 안전하지 않으며, 동시에 돌리면 메모리도 겹친다. 그래서 한 번에 하나만 돌려야 한다.
  - 처음엔 하나의 직렬 체인(unique work + `APPEND`)을 추천했다. 그런데 `APPEND` 체인은 **앞 작업이 실패하면 뒤에 붙은 작업까지 모두 실패 처리**된다. 녹음 하나가 "음을 못 찾음"으로 실패하면 뒤의 녹음이 같이 실패한다. 실패를 성공으로 위장해 체인을 이어 가는 방법도 있지만 상태의 의미가 흐려진다.
  - → **녹음마다 독립 작업**(`transcribe-<recordId>`, `ExistingWorkPolicy.KEEP`)에, 모델에 들어가는 구간만 앱 안에서 직렬화. `KEEP`이라 같은 녹음을 여러 번 눌러도 작업은 하나다. 끝난 작업은 `KEEP`이어도 새로 바뀌므로 실패 후 다시 시도가 된다.
- **결정 4: 앱 안의 직렬화를 무엇으로 — Mutex, Channel(mailbox/actor), 단일 스레드 디스패처**
  - **Channel + 소비자 코루틴 하나(actor 패턴)**: 모델을 소유한 코루틴 하나가 메일박스(Channel)에서 요청을 하나씩 꺼내 처리하고 `CompletableDeferred`로 답한다.
    - 장점: 공유 자원의 소유자가 하나라 잠금이 필요 없다. 요청이 메시지라 순서(FIFO)·우선순위·중복 합치기·대기 순번 표시("3번째") 같은 정책을 한곳에서 다룰 수 있다. 서로 다른 종류의 요청이 같은 상태를 바꿀 때 특히 좋다.
    - 우리 상황에서의 문제
      1. **큐가 두 개가 된다.** 영속 큐는 이미 WorkManager다. Channel은 메모리 큐라 프로세스가 죽으면 사라진다. Worker는 어차피 Channel에 보내고 답을 기다리며 자리를 차지하므로, Mutex를 기다리는 것과 얻는 게 같다. 대신 두 큐를 맞춰야 하는 부담만 생긴다.
      2. **취소가 저절로 전파되지 않는다.** 시스템이 Worker를 멈추면 Worker는 답 기다리기를 그만두지만, 메일박스에 들어간 요청은 남아 소비자가 그대로 처리한다(헛일). 요청마다 취소 상태를 확인하는 코드를 따로 넣어야 한다. `Mutex.withLock`은 기다리는 중에 취소되면 대기열에서 그냥 빠진다.
      3. **항상 살아 있는 코루틴의 수명 관리.** 소비자를 앱 스코프에서 띄워 두어야 하고, 처리 중 예외로 소비자가 죽으면 이후 요청이 모두 멈춘다(감독·재시작 필요). 표준 `actor {}` 빌더는 오래 `@ObsoleteCoroutinesApi` 상태라 직접 만들어야 한다.
    - Channel이 맞는 경우: WorkManager 없이 앱 안에서만 도는 큐이거나, 우선순위·합치기·대기 순번 표시가 요구사항일 때.
  - **단일 스레드 디스패처(`limitedParallelism(1)`)**: blocking 코드만 있으면 직렬화되지만, 안에서 suspend(파일 IO를 위한 `withContext` 등)하면 그 사이에 다른 작업이 끼어든다. "한 작업이 끝날 때까지 독점"을 보장하지 못한다.
  - **Mutex**: 문제의 본질이 "메시지 처리"가 아니라 "자원 하나에 대한 상호 배제"라 그대로 표현된다. 기다리는 중 취소가 안전하고, 항상 살아 있는 코루틴이 필요 없다. kotlinx의 Mutex는 공정해서 대체로 들어온 순서로 처리된다(엄격한 순서 보장은 아님).
  - → **Mutex**. 기다리는 동안은 진행 정보에 `WAITING`을 올려 화면에 "대기 중"으로 보인다.
- **결정 5: 다시 실행돼도 결과가 같게(멱등)**
  - WorkManager는 프로세스가 죽거나 시스템이 작업을 멈추면 작업을 다시 실행한다. DB에 저장은 됐는데 성공 보고 전에 죽으면 악보가 두 개 생길 수 있다.
  - → 악보 id를 시각(`score_<now>`)이 아니라 **작업 id**에서 만들고 같은 id는 덮어쓴다. 파일은 임시 이름으로 쓴 뒤 이름을 바꾸고 → DB 저장 → 성공 보고. Worker가 시작할 때 이 작업 id로 남은 임시 파일을 지운다.
- **결정 6: 취소**
  - 사용자 취소 버튼은 두지 않는다. 대신 시스템이 멈출 때를 위한 협조적 취소를 넣는다. 단계 사이에서 확인하고, 추론은 suspend가 아닌 blocking 루프라 `predict`의 진행률 콜백 안에서 확인해 빠져나온다. 멈춤은 실패가 아니라 WorkManager가 다시 예약한다.
  - 대기 중인 녹음을 지우면 녹음 삭제 유스케이스가 그 작업도 취소한다(내부 정리). 이미 시작했다면 녹음을 못 찾아 `RECORD_GONE`으로 끝난다. 악보를 지우면 Room 흐름으로 항목이 "채보하기"로 돌아간다.
- **결정 7: 경쟁 상태(race condition)를 어떻게 다루나**
  - 접근: 경쟁은 테스트로 "없음"을 증명할 수 없으므로, **공유되는 가변 상태를 셋으로 줄이고 각각에 규칙을 하나씩** 둔다. 모델(상호 배제), DB·파일(멱등), 화면 상태(도착 순서 규칙).
  - **모델 — Mutex 사용 규칙**
    - `lock()/unlock()`을 직접 쓰지 않고 `withLock`만. 예외·취소에도 `finally`로 풀린다.
    - 잠그는 범위는 추론만(읽기·쓰기는 밖). 범위가 좁을수록 대기와 실수가 준다.
    - Mutex는 한 클래스 안의 private 하나. Kotlin Mutex는 재진입이 안 돼 잠근 채로 다시 잠그면 스스로를 기다린다(데드락). 잠그는 곳이 한 군데면 중첩이 생기지 않는다.
    - 잠근 채 취소: 추론은 blocking 루프라 취소를 모른다. 진행률 콜백에서 취소를 확인해 예외로 빠져나와야 잠금이 풀린다. 없으면 취소된 작업이 추론을 끝까지 돌며 다음 작업을 막는다.
    - 모델의 첫 생성은 Hilt `@Singleton`이 동기화하지만, 생성도 잠금 안에서 해 첫 생성 비용이 다른 작업과 겹치지 않게 한다.
  - **DB·파일 — 같은 작업이 겹쳐 돌 수 있다**
    - WorkManager가 작업을 멈추고 다시 예약할 때, 옛 실행이 blocking 추론 중이면 아직 끝나지 않은 채 새 실행이 시작될 수 있다. 추론은 Mutex로 겹치지 않고, 파일은 **실행마다 다른 임시 이름**으로 쓴 뒤 최종 이름으로 원자적 rename, DB는 작업 id에서 만든 같은 악보 id로 REPLACE. 둘 다 끝까지 가도 같은 악보 하나.
    - **TOCTOU: 채보 중 녹음 삭제.** Worker가 녹음을 읽은 뒤 사용자가 지우면, 오디오는 메모리에 있어 추론은 계속되지만 마지막 저장에서 **외래 키가 없는 녹음을 가리켜 실패한다**(초안에서 놓친 경우). → 외래 키 실패·WAV 읽기 실패는 녹음이 아직 있는지 다시 확인해 `RECORD_GONE`으로 바꾸고 쓴 파일을 지운다.
    - 같은 녹음 두 번 누르기·두 화면에서 누르기는 `KEEP`이 WorkManager 자체 DB 트랜잭션 안에서 막는다(우리 쪽 경쟁 없음).
  - **화면 상태 — 두 흐름의 도착 순서**
    - 화면은 WorkInfo(WorkManager의 DB)와 악보 목록(우리 Room DB)을 합친다. **두 DB 사이엔 순서 보장이 없어**, 우리 저장이 먼저 끝나도 "성공" 신호가 화면에 먼저 올 수 있다 → `Running(95%) → Idle("채보하기") → HasScore` 깜빡임.
    - 검토: 성공을 `Saving` 상태로 두면, 나중에 사용자가 악보를 지웠을 때 남아 있는 성공 기록 때문에 "저장 중"에 갇힌다.
    - 결정: **"직전에 Running이었고, 작업 상태가 사라졌고, 악보는 아직 없다" → 악보가 나타날 때까지 "저장 중" 유지.** 성공 신호는 DB 저장 뒤에만 나오므로 악보는 반드시 곧 나타난다. 앱을 새로 띄우면 직전 상태가 없으니 Room만 보고 판단해 갇히지 않는다. ViewModel이 직전 상태를 기억하는(scan) 순수 함수로 두고 두 순서를 각각 테스트한다.
    - 진행률: blocking 콜백에서는 `setProgressAsync`를 쓴다. WorkManager의 직렬 실행기로 들어가 순서가 뒤바뀌지 않는다.
    - 초안의 ViewModel 메모리 안 "이미 실행 중" 검사(`showTranscribeInProgressMessage`)는 지운다. 중복은 `KEEP`이 전역으로 막고, 화면마다 따로 든 상태는 오히려 어긋난다.
  - **검증 방식**: 반복 실행(스트레스)으로는 잘 안 잡히므로, `CompletableDeferred`를 문처럼 써서 가짜 모델이 테스트가 열어 줄 때까지 멈춰 있게 하고 **원하는 실행 순서를 직접 만든다**.
    - 동시에 두 개 시작해도 모델 안에 동시에 있는 작업은 최대 1
    - 잠금을 기다리다 취소되면 대기열에서 빠지고 다음 작업이 진행
    - 추론 중 취소되면 잠금이 풀림
    - 같은 작업 id로 두 번 실행해도 악보 하나
    - 저장 단계 외래 키 실패 → `RECORD_GONE`, 파일이 남지 않음
    - 화면 상태: "성공 먼저·악보 나중"과 "악보 먼저·성공 나중" 모두 깜빡임 없이 `HasScore`
- **같이 정한 것**
  - 끝나도 화면을 자동으로 옮기지 않는다(사용자가 이미 다른 화면에 있을 수 있음). 라이브러리 항목에 "악보 보기"를 띄운다.
  - 자동 재시도 없음: 같은 녹음은 다시 돌려도 결과가 같다.
  - `setProgress`는 호출마다 WorkManager DB에 쓰므로 1% 이상 바뀔 때만 올린다.
  - 초기화: `MainApplication`이 `Configuration.Provider` + `HiltWorkerFactory`. 기본 자동 초기화는 매니페스트에서 `tools:node="remove"`로 뺀다(안 빼면 주입이 안 되는 기본 초기화가 먼저 돈다).
  - 기기 재현용 로그: 작업 id, `recordId`, `runAttemptCount`, 단계.
- **검증 계획**(B-17 원칙): 상태 변환 순수 함수(표의 경우), 실제 Worker + 가짜 저장소(`TestListenableWorkerBuilder`), 실제 WorkManager를 동기로(`WorkManagerTestInitHelper` + `SynchronousExecutor`: `KEEP` 중복 방지, 삭제 시 취소), 저장소(Mutex 직렬화, 같은 id로 다시 실행해도 악보 하나), ViewModel(가짜 Scheduler + 가짜 악보 흐름).
- **구현하며 알게 된 것 (3-1, 저장소)**
  1. **`runCatching`은 취소까지 삼킨다.** 초안은 파이프라인 전체를 `runCatching`으로 감쌌다. `runCatching`은 `CancellationException`도 잡아 `Result.failure`로 바꾸므로, 취소된 작업이 "실패"로 보고된다. Worker가 이를 실패로 넘기면 WorkManager가 다시 예약하지 않는다. → `try`에서 `CancellationException`만 다시 던지고 나머지를 `Result`로 바꾼다.
  2. **회귀가 생기면 테스트가 실패하지 않고 멈췄다.** 변이 검사로 "진행률 콜백의 취소 확인"을 지웠더니, 취소된 작업이 가짜 모델 안에서 영원히 돌았다. `runBlocking`이 그 작업을 기다리며 테스트 프로세스 전체가 멈췄다. 변이를 "잡긴" 했지만, CI에서는 실패가 아니라 무한 대기로 나타나 원인을 알기 어렵다. → 가짜 모델에 상한(5초)을 두고, 넘으면 `AssertionError`를 던진다. `Exception`이 아니라 `Error`라 저장소가 실패 결과로 삼키지 못한다. 다시 돌리니 세 변이 모두 **실패로** 잡혔다.
  3. **잡히지 않은 변이가 실제로는 같은 코드였다.** "취소를 다시 던지는 catch"를 지워도 테스트가 통과했다. 따라가 보니 `withContext`는 블록이 끝날 때 코루틴이 이미 취소됐으면 결과를 버리고 `CancellationException`을 던진다(prompt cancellation 보장). 그래서 이 구조에서는 catch가 없어도 취소가 새어 나가지 않는다. catch는 방어용으로 남기고, "저장소가 실제로 값을 돌려줬는지"를 기록하는 확인을 테스트에 더했다. 취소된 코루틴은 본문이 값을 돌려줘도 `isCancelled`가 true라 그것만으로는 이 계약을 볼 수 없기 때문이다. 나중에 `withContext`가 빠지면 이 확인이 잡는다.
  - 변이 검사 결과(실제 코드를 일부러 망가뜨림): Mutex 제거, 콜백 취소 확인 제거, RECORD_GONE 재확인 제거, 임시 파일 정리 제거, 저장 실패 시 파일 삭제 제거 → 모두 해당 테스트가 실패. 원래 코드로 세 번 연속 통과(각 약 0.55초).
- **구현하며 정한 것 (3-2, WorkManager)**
  1. **한 녹음에 작업 기록이 여럿일 수 있다.** 실패한 뒤 다시 누르면 `KEEP`이어도 새 작업이 생긴다(`KEEP`은 끝나지 않은 작업만 지킨다). 그래서 태그로 목록을 보면 같은 녹음의 옛 실패와 새 작업이 함께 온다. → 녹음별로 **진행 중 > 성공(표시 안 함) > 실패** 순으로 하나를 고른다. 순서가 반대면 "다시 시도해 성공했는데 예전 실패가 보이는" 일이 생긴다. 이 경우를 테스트로 고정했다.
  2. **녹음 id는 태그로 싣는다**(`transcription-record:<id>`). WorkInfo의 입력 데이터는 목록 조회에 나오지 않아서, 화면이 "어느 녹음의 작업인지" 알려면 태그가 필요하다.
  3. **모르는 값은 OTHER로.** 실패 이유·단계는 문자열로 저장되므로, 앱을 업데이트해 enum이 바뀌면 예전 작업 기록에서 모르는 값이 나올 수 있다. 변환이 죽지 않고 OTHER(단계는 READING)로 읽는다.
  4. **기본 초기화 제거 확인.** 매니페스트의 `tools:node="remove"`가 실제로 먹었는지 병합된 최종 매니페스트를 봤다. startup 항목에 `WorkManagerInitializer`가 없고 `EmojiCompatInitializer`만 남았다.
  - 테스트: 상태 변환 9개(순수 JVM, B-18 표 그대로), Worker 5개, 실제 WorkManager(테스트 초기화) 위의 Scheduler 6개, 녹음 삭제 1개. 변이 검사 5개(`KEEP`→`REPLACE`, 악보 id를 시각으로, Worker가 취소를 실패로 삼킴, 성공 우선순위 제거, 삭제 시 작업 취소 제거) 모두 해당 테스트가 실패. 원래 코드로 세 번 연속 통과.
- **구현하며 정한 것 (3-3, 라이브러리 화면)**
  1. **채보 상태를 ViewModel 메모리에 따로 들지 않는다.** 초안은 `TranscribeState`(진행 중인 녹음 하나)를 ViewModel이 들고, "이미 채보 중" 안내를 직접 띄웠다. 이제 항목 상태는 작업 흐름과 악보 흐름에서만 나온다. 그래서 화면을 다시 열어도(새 ViewModel) 같은 상태가 나오고, 녹음별로 따로 보인다. 중복 등록은 `KEEP`이 막으므로 "이미 채보 중" 안내와 그 문자열을 지웠다.
  2. **"저장 중" 규칙은 순수 함수 하나**(`reduceTranscriptions(previous, jobs, scores)`)이고, ViewModel은 `combine` → `scan`으로 직전 상태만 넘긴다. 이벤트를 차례로 밀어 넣는 테스트로 두 도착 순서(성공 먼저/악보 먼저), 대기에서 바로 끝난 경우, 앱을 새로 띄운 경우, 악보 삭제를 고정했다. 변이 검사: 악보 우선 규칙 제거, ViewModel이 직전 상태를 넘기지 않음, 저장 중 유지 제거 → 모두 해당 테스트가 실패.
  3. **결과 안내는 스낵바 대신 항목에 남긴다.** 실패 이유("멜로디를 찾지 못했어요")가 항목 아래에 남고, 버튼은 다시 "악보 만들기"라 바로 다시 시도할 수 있다. 끝나면 버튼이 "악보 보기"로 바뀐다(자동 이동 없음).
  4. 오픈소스 고지 문자열(`oss_notices`)은 아직 보여 줄 화면이 없어 이 커밋에서 뺐다(작업 트리에만 있음).
- **초안에서 같이 고칠 것**: WIP `TranscriptionRepositoryImpl`은 패키지가 옮겨진 `MidiWriter`를 옛 경로로 import하고, 지금은 class인 `HummingTranscriber`를 object처럼 불러 컴파일되지 않는다. `BasicPitchModel`·`ScoreTranscriber`를 생성자로 주입받게 정리한다.

## C. 기존 코드 개선(리팩터링)

마감에 맞춰 "돌아가게만" 만든 예전 코드를 온디바이스 전환과 함께 고친다. 범위는 온디바이스 흐름(녹음 → 라이브러리 → 채보 → 악보)이 지나는 코드로 한정하고, 그 밖에서 눈에 띈 것은 [개선 후보](#개선-후보)에만 적는다.
각 항목: `예전 코드 → 왜 문제인가(근거·깨지는 시나리오) → 검토한 대안 → 개선 → 검증`.

**판단 기준(악보 feature)**: 고치기보다 **다시 쓴** 이유 — 예전 화면은 "서버가 준 URL의 HTML을 보여 준다"는 전제로 짜여 있어(경로에 URL, 화면에서 HTTP, 외부 도메인을 base로 하는 WebView) 온디바이스 전환 후 남길 흐름이 거의 없었고, 계층 위반이 구조에 박혀 있어 부분 수정으로 풀리지 않았다. 레이아웃이 쓸 만한 목록 항목·빈 화면은 유지했다.

### C-1. domain 모델이 표시용 날짜 문자열을 들고 있었다

- **예전 코드**: `SheetMusic.createdAt: String`("yyyy-MM-dd HH:mm"). 매퍼가 저장할 때 `SimpleDateFormat(..., Locale.getDefault()).parse()`로 다시 숫자로 바꿨다. 한 화면은 초까지 있는 다른 형식("yyyy-MM-dd HH:mm:ss")으로 만들었다.
- **왜 문제인가**
  - 표시 형식은 화면의 관심사인데 domain이 들고 있다. 형식을 바꾸면 저장·파싱까지 영향이 간다.
  - 같은 값을 두 형식으로 만들고 한 형식으로 파싱했다. 초까지 있는 문자열은 `SimpleDateFormat`이 앞부분만 읽어 **우연히** 통과했고, 파싱이 실패하면 `?: System.currentTimeMillis()`로 **조용히 현재 시각으로 바뀌는 구조**였다(저장일이 틀어져도 오류가 안 남).
  - 기기 Locale로 파싱하므로 언어 설정에 따라 숫자·달력 표기가 달라지면 파싱이 깨질 수 있다.
- **개선**: domain·DB 모두 epoch ms(`Long`). 표시는 화면에서 `DateFormat.getDateTimeInstance(MEDIUM, SHORT, locale)`로 사용자 언어에 맞춰 한다(`formatCreatedAt`).

### C-2. 화면 사이에 URL 두 개를 경로 인자로 넘겼다

- **예전 코드**: `sheet_music_route/{scoreUrl}/{midiUrl}`. 두 URL을 `URLEncoder`로 인코딩해 경로에 실었다. 악보 목록·라이브러리가 각자 URL을 만들어 넘겼다.
- **왜 문제인가**
  - 화면이 받은 값이 저장된 값과 같다는 보장이 없다(두 곳에 진실이 있음). 상세 화면은 받은 URL로 악보를 **다시 DB에 저장**하기까지 했다.
  - 경로에 긴 값·특수문자를 실으면 인코딩 실수 하나로 내비게이션이 깨진다.
  - 프로세스가 죽었다 복원될 때 경로 인자만 남는데, 그 값이 이미 지워진 악보를 가리킬 수 있다.
- **개선**: 경로에는 악보 **id만**(`sheet_music_route/{scoreId}`). 상세 화면은 id로 저장소에서 읽는다(단일 진실 공급원). 지워진 id면 "악보를 찾을 수 없어요" 상태를 보여 준다.

### C-3. 타입이 없는 유스케이스 입력과 더미 구현

- **예전 코드**: `GetSheetMusicDetailUseCase(requestBody: Any)`, `SheetMusicRepository.generateSheetMusic(requestBody: Any)`. 구현은 입력을 쓰지 않고 "새 악보"라는 빈 더미를 만들어 저장했다. 화면의 "샘플 악보 생성하기" 버튼이 이 경로를 불렀다.
- **왜 문제인가**: `Any`는 컴파일러가 아무것도 검사해 주지 않는다. 이름은 "상세 조회"인데 하는 일은 "더미 생성 + 저장"이라, 이름만 보고 쓰면 빈 악보가 DB에 쌓인다. 실제 기능이 아닌 경로가 사용자 화면에 노출돼 있었다.
- **개선**: 더미 경로를 지우고, 이름과 하는 일을 맞췄다. `GetSheetMusicDetailUseCase(id: String): Result<Detail?>`(악보 + MusicXML 본문, 없으면 null). 악보 생성은 채보(3단계)만 한다.

### C-4. ViewModel이 저장소를 직접 주입받았다

- **예전 코드**: `ScoreHistoryViewModel(sheetMusicRepository)`, 상세 ViewModel도 유스케이스와 저장소를 함께 받았다.
- **왜 문제인가**: 이 프로젝트는 이전 리팩터링에서 "ViewModel은 저장소 대신 유스케이스를 받는다"로 정했는데(`a599fa1`), 악보 feature만 빠져 있었다. 규칙이 섞이면 다음 사람이 어느 쪽을 따라야 할지 모르고, ViewModel이 저장소의 모든 메서드(저장·삭제)에 손이 닿는다.
- **개선**: `GetScoresUseCase`, `DeleteScoreUseCase`, `GetSheetMusicDetailUseCase`만 받는다.

### C-5. 화면이 ViewModel 상태를 직접 읽어 "불러올지"를 정했다

- **예전 코드**: 화면의 `LaunchedEffect(scoreUrl, midiUrl)`에서 `viewModel.uiState.value`를 읽어 "이미 같은 URL로 성공했으면 생략"하고, 아니면 `loadUploadedFiles()`를 불렀다.
- **왜 문제인가**: 상태의 흐름이 화면 → ViewModel → 화면으로 되돌아온다(단방향이 아님). 구성 변경·재구성 때 언제 다시 불러오는지가 화면 코드 곳곳의 조건에 달려 있어 추적하기 어렵다.
- **개선**: ViewModel이 `SavedStateHandle`로 내비게이션 인자(id)를 받아 `init`에서 스스로 불러온다. 화면은 상태(`Loading / Success / NotFound / Error`)를 받아 그리기만 하고, 사용자 행동(다시 시도)만 위로 올린다. 화면 본문은 상태만 받는 `SheetMusicContent`로 분리해 미리보기·테스트가 쉽다.

### C-6. 화면(Composable)이 네트워크를 직접 호출했다

- **예전 코드**: `RemoteScoreViewer`가 Composable 안 `LaunchedEffect`에서 `HttpURLConnection`으로 서버 HTML을 받아 상태 변수에 넣었다.
- **왜 문제인가**: UI 계층이 데이터 계층의 일(네트워크·오류 처리·재시도)을 한다. 재구성마다 요청이 다시 나갈 수 있고, 테스트할 때 네트워크를 떼어 낼 수 없다. 오류 메시지 안에서 `connection.responseCode`를 다시 읽어 **오류 처리 중에 또 네트워크 호출**을 하고 있었다.
- **개선**: 온디바이스 전환으로 네트워크 자체가 필요 없어져 파일을 지웠다. 악보 본문(MusicXML)은 저장소가 읽어 ViewModel 상태로 내려 준다.

### C-7. WebView 보안 설정

- **예전 코드**(`MusicScoreWebView`): JavaScript를 켠 채 `MIXED_CONTENT_ALWAYS_ALLOW`, `allowFileAccess = true`, `allowContentAccess = true`, 외부 서버 도메인을 base URL로 `loadDataWithBaseURL`.
- **왜 문제인가**: 서버가 준 HTML을 그대로 실행하는데, HTTPS 페이지 안의 HTTP 리소스도 허용하고 로컬 파일 접근까지 열려 있었다. 중간자가 HTTP 리소스를 바꾸면 그 스크립트가 앱 WebView 권한(파일 접근, JS 브리지)으로 실행될 수 있다.
- **개선**: 파일을 지웠다. 새 렌더러(2-2)는 앱 assets의 고정 페이지만 `WebViewAssetLoader`의 가상 https 주소로 열고, `allowFileAccess`·`allowContentAccess`를 끈다. 네트워크 리소스는 쓰지 않는다.

### C-8. 녹음을 지우면 악보가 없는 녹음을 가리켰다

- **예전 코드 / 첫 초안**: 악보 테이블에 녹음과의 관계가 없었고, 초안에서 넣은 `recordId`도 외래 키가 아니었다.
- **왜 문제인가**: 녹음을 지우면 악보의 `recordId`가 존재하지 않는 행을 가리킨다. 나중에 "이 악보의 원본 녹음 듣기" 같은 기능이 그 id를 믿으면 깨진다.
- **검토한 대안**: (1) 녹음과 함께 악보도 지우기(CASCADE) (2) 악보는 남기고 연결만 끊기(SET_NULL). 악보는 사용자가 공유·보관하는 결과물이라 녹음과 수명이 같지 않다고 보고 (2)를 택했다.
- **개선**: Room 외래 키 `onDelete = SET_NULL` + `record_id` 인덱스. DB v8.

### C-9. 화면에 하드코딩된 문자열

- **예전 코드**: `"악보 확인"`, `"뒤로 가기"`, `"저장일: ..."`, `"다시 시도"`, `"오류가 발생했습니다"` 등이 Composable 안에 한국어로 박혀 있었다.
- **왜 문제인가**: 앱은 한국어·영어를 지원하는데(리소스 모듈화) 이 화면만 영어 설정에서도 한국어가 나온다. 접근성 설명(contentDescription)도 번역되지 않는다.
- **개선**: 모두 `core:resources`의 문자열로 옮겼다(3개 언어 파일). 값을 이어 붙이던 곳은 포맷 문자열(`%1$d BPM · %2$s · …`)로 바꿔 언어별로 순서를 바꿀 수 있게 했다.

### C-10. 쓰지 않는 INTERNET 권한과 이미지 라이브러리

- **예전 코드**: 앱과 `feature:sheetmusic` 매니페스트에 `INTERNET` 권한, `feature:sheetmusic`에 Coil(이미지 로딩) 의존성.
- **왜 문제인가**: 서버 채보 시절의 흔적이다. 온디바이스 전환 뒤에는 네트워크를 쓰는 코드가 없는데 권한이 남아 있으면, 사용자에게 "인터넷을 쓰는 앱"으로 보이고 나중에 실수로 네트워크 코드가 들어와도 막히지 않는다. Coil은 import하는 곳이 없었다.
- **확인한 것**: Retrofit·OkHttp·Firebase 등 네트워크 라이브러리가 gradle에 남아 있지 않음. 악보 WebView의 `https://appassets.androidplatform.net/...` 주소는 `WebViewAssetLoader`가 앱 안에서 가로채 응답하므로 실제 네트워크를 타지 않는다.
- **개선**: 두 매니페스트의 `INTERNET`과 Coil(버전 카탈로그 포함)을 지웠다.
- **검증**: 라이브러리 매니페스트까지 병합한 최종 매니페스트에 `INTERNET`이 없음(남은 권한: 녹음, 오디오 읽기, AndroidX 내부용 하나. 그 뒤 오디오 읽기는 지웠고 WorkManager의 일반 권한 넷이 더해졌다 → C-12). 디버그 APK 빌드 성공.
- **남은 것**: `README_ko.md`가 아직 Retrofit·Firebase를 설명한다. 마지막 문서 정리 때 고친다.

### C-11. 오픈소스 고지가 실제로 배포되는 것과 맞지 않았다

- **예전 코드**: About 화면에 "본 앱은 다양한 오픈소스 라이브러리를 기반으로 제작되었습니다. 라이선스 정보 확인하기"라는 문구만 있고, 누를 곳도 목록도 없었다. 온디바이스 전환 중에 만든 고지 초안(`oss_notices`)은 Basic Pitch, LiteRT, OSMD 세 개만 적은 한 줄짜리 문자열이었다.
- **왜 문제인가**
  - MIT·BSD-3·Apache-2.0은 소스 공개를 요구하지 않는 허용적 라이선스지만, **바이너리(APK)를 배포할 때 저작권 문구와 라이선스 원문을 함께 제공**하라는 조건이 있다. Apache-2.0은 NOTICE 파일이 있으면 그 내용도 보이라고 한다. 저장소를 오픈소스로 공개하는 것만으로는 APK 배포 조건이 채워지지 않는다.
  - 초안의 세 개는 실제로 실리는 것보다 훨씬 적었다. OSMD의 압축된 번들 안에는 다른 라이브러리가 함께 들어 있다.
- **확인한 방법**(추측으로 적지 않기)
  1. OSMD 3.0.0의 `package.json`: 런타임 의존성은 jszip·typescript-collections, 빌드할 때 vexflow·loglevel도 번들된다.
  2. 각 라이브러리의 해당 버전 LICENSE 파일에서 저작권 문구를 원문 그대로 옮겼다. `immediate`는 공개 저장소 경로가 404여서 npm 패키지 압축 파일(3.0.5)을 받아 `LICENSE.txt`를 직접 읽었다.
  3. JSZip이 끌고 오는 라이브러리는 **우리 assets의 번들 코드**에서 확인했다: pako·lie·immediate·setimmediate는 들어 있고, readable-stream은 `require("stream")` 자리만 있고 비어 있어(`stream: void 0`) 들어 있지 않다.
  4. JSZip은 MIT 또는 GPLv3 중 고르는 이중 라이선스라, **MIT로 쓴다고 명시**했다(GPL 의무가 생기지 않게).
- **결정**
  - About 화면 맨 아래에 목록을 두고, 항목을 누르면 원문(과 NOTICE)이 펼쳐진다. 고지 대상: Basic Pitch(Apache-2.0 + NOTICE), LiteRT, OSMD(BSD-3), VexFlow, JSZip, pako, lie, immediate, setImmediate, typescript-collections, loglevel(MIT), AndroidX·Kotlin·Dagger/Hilt(Apache-2.0).
  - **목록은 코드로 직접 관리**(`OpenSourceLicenses.kt`). 자동 생성 도구(AboutLibraries, Google oss-licenses 플러그인)는 Maven 의존성만 모아 주고 JS 번들·모델은 어차피 손으로 넣어야 한다. Google 플러그인은 Play Services 의존성도 더한다. 대신 의존성이 바뀌면 이 목록도 고쳐야 한다(남은 과제).
  - **원문은 이 모듈의 assets에 복사**했다. 다른 모듈의 assets 경로(`basic_pitch/LICENSE`)를 가리키면 중복은 없지만, 모듈 사이에 파일 경로로 숨은 연결이 생긴다. 라이선스 원문은 바뀌지 않는 글이라 복사가 낫다고 봤다. 공용 원문(MIT·Apache)에는 저작권 줄을 빼고, 화면에서 항목의 저작권을 앞에 붙인다.
- **진행 중 발견한 것: assets가 APK에서 바이트가 달라졌다**
  - APK를 열어 assets 크기를 원본과 비교했더니, 라이선스 원문이 줄 수만큼 커져 있었다(Apache 원문 11,357 → 11,558바이트, 201줄). `core.autocrlf=true`인 Windows에서 체크아웃하며 LF가 CRLF로 바뀐 것이다. Basic Pitch의 LICENSE·NOTICE도 같았다.
  - 4-1에서 `.gitattributes`를 OSMD 폴더에만 걸어 둔 것이 너무 좁았다. → `**/src/main/assets/** -text`로 넓혔다. 다시 빌드한 APK에서 assets 11개 모두 저장소와 바이트 수가 같다.
- **검증**: 목록의 모든 원문·NOTICE 파일이 있고 비어 있지 않음, 모든 항목에 저작권 문구, 공용 원문에 다른 저작권이 섞이지 않음, OSMD 원문에 OSMD 저작권 포함(JVM 테스트 4개). lint 오류 0.
- **남은 것** 📝: 의존성·OSMD·모델을 바꿀 때 목록을 같이 고친다. 법적 효력은 보장하지 않으므로 실제 배포 전에 목록을 한 번 검토한다.

### C-12. 약관이 서버 시절 그대로였고, 앱도 "기기 안에서만"을 다 지키지 못했다

- **예전 코드**: 설정의 이용약관·개인정보 처리방침(`TermData.kt`)이 서버 채보 시절 내용이었다. "구글 계정 연동 회원제", "음성 파일은 서버에서 즉시 파기(선택 동의 시 AI 학습용 익명 보관)", "자동화 봇 대량 생성 요청 금지", 수집 항목에 구글 계정·접속 로그·기기 정보.
- **왜 문제인가**: 사용자에게 보이는 법적 문서가 실제 동작과 다르다. 지금 앱은 로그인이 없고 서버도 없다.
- **약관을 쓰기 전에 "사실"부터 확인했다** — 약관에 "녹음은 기기 밖으로 나가지 않는다", "권한은 마이크 하나"라고 쓰려면 코드가 실제로 그래야 한다. 확인해 보니 두 군데가 어긋났다. 둘 다 우리가 만든 기능이 아니라 프로젝트 템플릿에서 남은 설정이라 눈에 잘 띄지 않았다.
  1. **OS 자동 백업**: 매니페스트가 `allowBackup="true"`이고 백업 규칙은 템플릿 그대로(비어 있음)였다. 이러면 사용자가 기기 백업을 켜 둔 경우 **Android가 앱 내부 저장소(녹음·악보·DB)를 사용자의 Google 드라이브에 올린다**. 백업 코드를 짠 적이 없어도 그렇다.
  2. **쓰지 않는 권한 요청**: 앱 시작(온보딩) 때 마이크와 함께 `READ_MEDIA_AUDIO`(13+)·`READ_EXTERNAL_STORAGE`(12 이하)를 요청했다. 녹음·악보는 모두 앱 내부 저장소라 쓰는 곳이 없었다.
- **검토한 선택지**: (a) 앱을 "기기 안에서만"에 맞추고 그대로 적는다, (b) 동작은 두고 약관에 "본인 Google 백업에 포함될 수 있음", "오디오 파일 읽기 권한을 요청함"을 밝힌다. 이 앱의 핵심 약속이 "녹음이 기기 밖으로 나가지 않는다"라서 (a). 동작 변경(4-3a)과 문서 변경(4-3b)을 나눠 커밋해, 약관 문장이 근거로 삼는 동작이 먼저 들어가게 했다.
- **결정**
  - 백업: `allowBackup="false"` + `data_extraction_rules`에서 클라우드 백업은 모든 영역 제외. 사용자가 새 기기로 직접 옮기는 기기 간 이전은 기본값대로 둔다(본인 기기 사이). Android 11 이하 전용인 `backup_rules.xml`은 백업 자체가 꺼지므로 지우고, lint의 `DataExtractionRules` 경고는 이유를 적고 무시했다.
  - 권한: 매니페스트와 `MainActivity`에서 저장소·미디어 권한을 지우고 마이크 하나만 요청한다.
  - 약관: 바뀐 사실만 고쳤다(로그인 없음, 녹음은 기기 안에서만 변환·저장, 서비스가 녹음·악보를 수집·이용하지 않음, 서버 관련 금지 조항 삭제, 공유한 파일은 받는 앱의 정책, 클라우드 백업 없음·기기 간 이전은 가능). 책임자(팀 정보) 조항은 바뀐 사실이 아니라 그대로 뒀다.
- **진행 중 발견한 것: 라이브러리가 더한 권한** — 병합된 최종 매니페스트를 보니 3-2에서 넣은 WorkManager가 `WAKE_LOCK`, `ACCESS_NETWORK_STATE`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE`를 자동으로 더하고 있었다. 3-2 때 최종 권한 목록을 확인하지 않아 놓친 것이다. 모두 설치 때 OS가 묻지 않고 주는 **일반 권한**이고 인터넷 권한은 없다(`ACCESS_NETWORK_STATE`는 연결 여부만 본다). 빼면 WorkManager 내부(재부팅 후 작업 재등록 등)가 깨질 수 있어 두고, 처리방침에 "사용자에게 허락을 구하는 권한은 마이크 하나, 백그라운드 작업용 일반 권한은 자동 포함, 인터넷 권한 없음"으로 정확히 적었다. C-10의 "남은 권한" 목록도 이때부터는 이 넷이 더해진 상태다.
- **배운 점**: "우리 코드가 하지 않는다"와 "앱이 하지 않는다"는 다르다. OS 설정(백업)과 라이브러리가 병합하는 매니페스트까지 봐야 약관에 사실을 쓸 수 있다.
- **남은 것** 📝: 법률 자문이 아니므로 실제 배포 전에 약관을 검토한다. 의존성을 더할 때마다 최종 매니페스트의 권한을 확인한다.

### C-13. main으로 가는 PR이 lint에서 계속 막혔다

- **증상**: dev → main PR의 CI가 `:feature:library:lintDebug`에서 실패했다(`LocalContextGetResourceValueCall`). 같은 실패가 반복됐다.
- **실제 범위를 먼저 확인했다**: CI와 같은 `./gradlew lintDebug`를 `--continue`로 로컬에서 돌리니, 오류는 한 모듈이 아니라 **세 모듈에 6개**였다.

  | 모듈 | 규칙 | 위치 | 언제 생겼나 |
  |---|---|---|---|
  | feature:library | `LocalContextGetResourceValueCall` | `LibraryScreen.kt` 삭제 결과 스낵바 2곳 | 2026-03 코드 |
  | feature:record | `LocalContextGetResourceValueCall` | `RecordScreenState.kt` 저장 안내 2곳, 권한 안내 1곳 | 2026-11-04 코드 1곳, **이번 온디바이스 1단계에서 쓴 코드 2곳** |
  | feature:sheetmusic | `MissingClass` | 매니페스트의 `.SheetMusicActivity` | 2025-11-06에 클래스를 지우고 선언만 남음 |

- **원인 1 — 라이브러리 업그레이드가 들여온 새 규칙**: 2026-11-06(`a43b2e2`)에 `compose-bom`이 2024.10.00에서 2026.09.00으로 올랐다. 새 Compose UI lint가 "`LocalContext.current.getString()`으로 문자열을 읽으면 설정 변경(언어 등)을 따라가지 못해 옛 값이 남는다"를 **오류**로 추가했다. 걸린 코드 대부분은 그 전부터 있었고, 1단계에서는 그 기존 방식을 그대로 따라 썼다. 실제로도 문제가 되는 패턴이다. 앱 설정에서 언어를 바꾸면 붙잡아 둔 문구가 옛 언어로 남을 수 있다.
- **원인 2 — 지운 클래스의 매니페스트 선언**: 악보 화면을 Compose로 옮기며 `SheetMusicActivity`를 지웠지만 매니페스트 선언은 남았다. 2-4에서 같은 매니페스트의 `INTERNET` 줄만 지우고 이 줄은 놓쳤다.
- **원인 3 — 왜 반복됐나(두 겹으로 가려졌다)**
  1. **CI가 첫 실패에서 멈췄다.** `./gradlew lintDebug`에 `--continue`가 없어 Gradle이 첫 실패 모듈(library)에서 멈춘다. library를 고쳐도 다음 실행에서 record, 그다음 sheetmusic이 하나씩 드러나는 구조였다.
  2. **로컬 확인이 CI와 달랐다.** 온디바이스 작업 내내 `:app:lintDebug`만 돌리고 "lint 오류 0"이라고 보고했다. app 모듈의 lint는 기본 설정(`checkDependencies` 꺼짐)에서 라이브러리 모듈을 검사하지 않는다. 세 모듈이 실패하는 상태에서 잘못된 "통과"를 보고한 것이다.
- **같이 발견한 것 — CI가 돌리지 않던 테스트**: CI의 테스트 단계 `./gradlew testDebugUnitTest`는 안드로이드 모듈만 돈다. 순수 JVM 모듈(`core:domain`, `core:music`)의 테스트 작업 이름은 `test`라서, `core:music`의 골든 테스트·채보 알고리즘 테스트 42개와 `core:domain` 테스트가 **CI에서 한 번도 돌지 않았다**.
- **결정**
  - 인자 없는 문자열은 컴포지션에서 `stringResource(...)`로 읽어 effect에 넘긴다. 실행 시점에야 정해지는 인자가 있는 문자열(저장된 파일 이름)은 `LocalResources.current.getString(...)`으로 읽는다. 둘 다 설정 변경을 따라간다. lint 기준선(baseline)으로 덮지 않았다. 실제로 맞는 지적이라서다.
  - 매니페스트에서 `SheetMusicActivity` 선언을 지웠다.
  - CI: lint에 `--continue`를 넣어 모든 모듈의 결과가 한 번에 보이게 하고, 테스트 단계에 `:core:domain:test :core:music:test`를 더했다.
- **검증**: CI와 똑같은 세 명령(`lintDebug --continue`, 테스트, `assembleDebug`)을 스테이징된 스냅샷에서 차례로 돌렸다. lint는 모든 모듈 오류 0, 테스트 130개 통과, APK 빌드 성공.
- **배운 점**: "로컬에서 통과했다"는 CI와 같은 명령으로 확인했을 때만 의미가 있다. 멀티 모듈에서 lint·test는 모듈마다 따로 돌고, JVM 모듈은 작업 이름부터 다르다. 의존성을 크게 올리면 새 lint 규칙이 따라온다.
